结合当前实现，问题本质可以概括成：顶栏「搜索」是主入口，但语义能力的主开关和成本说明藏在侧栏「智能搜索增强」；而主分析链路里 caption 在无云 Key 时为 MODULE_DISABLED，自然语言检索所依赖的 ai_description / 标签 / FTS 文档往往为空或很弱。用户很容易以为「搜索坏了」，其实是「增强未配置或未完成」。

下面是一套不改代码的产品与信息架构设计方案。

一个概念：用户只理解「搜索」及其「增强档位」，不背「云模型 / 智能搜索增强」。

三、信息架构：双入口、一条故事线
3.1 主入口：搜索栏（发现 + 轻引导）
在 SearchBar 区域增加可折叠的状态条（非弹窗打断），三种状态对应三档：

状态	展示（示例）	主操作
未配置 Key
「语义搜索未开启：目前可按时间、地点、人物筛选；描述画面需先配置」
去开启 → 设置向导
已配置，覆盖率 < 100%
「语义索引进行中：已覆盖 1,240 / 3,800 张」
查看进度 → 导入处理中心 / 补跑页
已就绪
弱提示或仅图标：「语义搜索已开启」
点击可看说明与费用链接
Placeholder 随状态变化（很重要）：

未配置：搜索时间、地点，或人物…（描述画面需开启搜索增强）
已配置：试试：海边 sunset、宝宝第一次走路、发票上的公司名
零结果时分流文案（替代单一「没有找到相关结果」）：

未配置 + 查询像「语义句」→ 引导开启，并给 1～2 条「当前可用」示例（如「2024 北京」）。
已配置但该用户大量 analysis_status_cloud != success → 「部分照片尚未完成语义分析，可前往补跑」。
已配置且覆盖率高 → 保持现有「无结果」，可附带「试试更短的关键词」。
这样用户第一次在顶栏搜「小狗在草地」落空时，得到的是可行动解释，而不是「功能坏了」。

3.2 次入口：设置页（配置 + 成本 + 补跑）
保留现有 ProviderSettingsPage 能力，但重组叙事顺序：

这是什么（1 段）：为「搜索」生成可检索的描述，存在本机数据库。
你需要做什么（3 步卡片，可展开）
注册/登录阿里云百炼
创建「百炼通用 API Key」（sk-）
粘贴 → 测试 → 保存 Key
会产生什么费用（必读，但缩短为 bullet + 外链「计费说明」）
启用后支持（与搜索栏文案逐条对齐）
历史照片补跑（现有 rebuild 卡片）
隐私（现有 dataLocalOnly）
Key 获取：嵌入式向导（设计稿级）

步骤条 + 「在浏览器中打开控制台」按钮（deep link 到 API Key 管理页）。
图示区分 sk-（正确） vs sk-sp-（错误）。
测试连接成功前，主按钮文案为「保存 Key」，未测通时禁用，避免「已保存但未测通」的假象。
卡片右上角为「已配置 / 未配置」（非启用开关）；是否调用云模型由「自动生成」开关与「开始生成」按钮决定。
与「地点地图增强」并列时，副标题统一句式：

地点：让地址更细（可选）
搜索：让搜索更懂画面（可选）
用户能一眼看出：都是可选增强，不是基础功能坏了。

四、关键用户旅程
旅程 A：新用户，未配置 Key
导入照片 → 本地人脸/时间/地点可用。
顶栏搜索「去年夏天」→ 有结果（时间解析 + 筛选）。
搜「穿红裙子的女孩」→ 弱或无结果 → 状态条提示「语义搜索未开启」→ 向导配置。
配置成功 → 提示「新照片将自动分析；历史照片可一键补跑」。
成功标准：用户能说清「没配 Key 也能搜时间和地方，描述画面要开增强」。

旅程 B：已配置，历史库大
设置页启用 → 自动或引导「补跑」。
顶栏显示进度条或分数。
补跑期间搜索：对已完成的媒体正常语义召回；对未完成的不误导（可在结果区脚注「结果仅包含已完成语义分析的照片」——可选，看是否接受范围缩小）。
旅程 C：对费用敏感，主动不用云
设置页明确：停用后不再产生云费用，基础搜索不受影响。
顶栏长期显示「基础搜索」态，placeholder 不再暗示语义能力。
与 costNotice 现有文案一致，但从「必读长段」升级为首屏 2 行 + 展开详情。

六、需要的产品数据与接口（实现时再做的契约，此处只列设计）
前端要做出上述体验，建议后端聚合一个搜索就绪状态（单次请求，避免各页各自 getCloudModelSettings）：

// 概念结构，非实现代码
SearchReadiness {
  tier: 'basic' | 'semantic_pending' | 'semantic_ready'
  cloudEnabled: boolean
  cloudKeyConfigured: boolean
  semanticIndexedCount: number   // analysis_status_cloud = success 且 ai_description 非空等规则
  semanticEligibleCount: number // 可参与语义分析的媒体总数
  rebuildInProgress: boolean
  estimatedCostHint?: string    // 可选，静态文案即可
}
覆盖率规则要在产品层定义清楚（例如：仅图片+视频且未删除、排除 cloud 内容安全拒绝等），与导入处理中心的「云分析阶段」统计对齐，避免两处数字不一致。

七、与「高德地点增强」的对齐策略
你们已有较好的 Provider 设置页模板（功能列表、隐私、补跑、测试连接）。建议：

交互同构：搜索增强与地点增强同一套步骤与按钮语义。
叙事差异：地点增强强调「未配置有本机降级」；搜索增强强调「未配置则语义召回不可用，但基础搜索仍在」。
导入处理中心：进度环旁用同一套「含 xxx 增强」句式，把 aiIncludesCloudHint 改成与顶栏状态条同一数据源。

九、需要产品层拍板的一个策略问题
当前实现是 无云 Key 则 caption 模块直接禁用，语义索引几乎完全依赖云。设计上两条路：

保持现状（推荐短期）

产品叙事诚实：语义搜索 = 可选云增强，基础搜索不夸大。
投入主要在引导与状态，而非重做本地 caption。
中长期

文档里已有 caption.provider=local 方向；若恢复本地 caption，可把三档改成「本地语义（弱）+ 云语义（强）」，降低对 Key 的硬依赖。
这属于架构演进，与本次 UX 方案可并行规划，但不阻塞 P0。
